### 1.3 Axis 3 — confidence

```text
HIGH
MEDIUM
LOW
```

Confidence is **evidence quality only**. It must never be moved by effect magnitude. Internally it is a `confidence_score` in `0.0 .. 1.0` mapped to the three labels (§14), so calibration can be refined later without changing the public schema.

"Extremely overtuned, confidence HIGH" and "Overtuned, confidence LOW" communicate two different things — effect size versus quality of evidence — and both are useful.

### 1.4 Axis 4 — analysis status

```text
COMPLETE
PARTIAL_STATIC
```

`analysis_status` is coverage, not conclusion. When it is `PARTIAL_STATIC`, the verdict is `null`:

```json
{ "analysis_status": "PARTIAL_STATIC", "verdict": null, "confidence": "LOW" }
```

This lets BalanceBench say *"I can see some of this thing, but not enough to certify it"* without forcing a dishonest `MANUAL` or a worse `WITHIN_VANILLA_BAND`. It is general, not fighter-specific.

Note the combination that matters most: you can be **highly confident that you cannot decide**:

```json
{
  "analysis_status": "COMPLETE",
  "verdict": "MANUAL",
  "manual_reason": "SCRIPT_BALANCE_UNKNOWN",
  "confidence": "HIGH"
}
```

### 1.5 Informational tag

```text
HIGH_END_REFERENCE
```

Attached when an entity is high-end by vanilla standards **but still inside the permitted tier envelope**. Example: under `--tier high_power`, a 94th-percentile weapon may be `WITHIN_VANILLA_BAND` + `HIGH_END_REFERENCE`. This distinguishes "ordinary vanilla-strength weapon" from "intentionally powerful weapon that lands where its author said it should". A tag never changes verdict, severity, or any count.

### 1.6 Canonical excess convention

Throughout the document:

```text
positive balance excess = candidate advantage
negative balance excess = candidate disadvantage
```

Every metric declares its direction (§10.0). A metric whose *lower* value is stronger (shield efficiency, flux/use, cooldown) is transformed before percentiles are taken, so this convention holds everywhere.

## 2. Scope

### 2.1 Phase 1 entities (v1)

```text
WEAPONS
HULLS
```

These two, done extremely well. A mediocre six-entity analyzer is less valuable than an excellent two-entity analyzer.

### 2.2 Phase 2 entities

```text
FIGHTERS
HULLMODS
SHIP SYSTEMS
```

Fighters arrive with `PARTIAL_STATIC` possible, because wing composition is only partly recoverable statically. Hullmods are compared cost-to-cost (§12.2).

### 2.3 Explicitly out of scope

- Combat simulation or any gameplay-equivalence claim. The static analyzer makes **no** claim about how content performs in battle.
- Runtime benchmarks — planned, separately labelled, and **deferred to Phase 4** (§23). The static analyzer never depends on them.
- Campaign-side balance (economy, fleet, market, exploration, colony content). **Out of scope through Phase 3.** Reconsideration requires a new approved design revision.
- Editing, patching, generating, or rebalancing mod content. BalanceBench is read-only and advisory.
- Legality/mod-compatibility auditing. That is VoidSmith's concern; BalanceBench consumes its output without duplicating it (§7).
