## 6. Table substrate

All parsing funnels into **canonical tables** before any analysis happens. Analysis code never reads `.wpn`, `.ship`, `.ship` JSON, or CSVs directly; it reads tables. This is what makes results reproducible and testable.

### 6.1 Weapon table (Phase 1)

```text
id                  weapon id (unique)
source              VANILLA_CORE | MOD:<modId>
weapon_type         BALLISTIC | ENERGY | MISSILE | OTHER
size                SMALL | MEDIUM | LARGE
damage_class        KINETIC | HE | FRAGMENTATION | ENERGY | OTHER
role                PD | STRIKE | SUPPORT | ASSAULT | OTHER
trigger             BURST | CONTINUOUS
delivery            PROJECTILE | BEAM | MISSILE | OTHER
ammo_model          UNLIMITED | AMMO | MISSILE_AMMO
is_pd               bool
turret_behaviour    NONE | TURRET | FIXED | OTHER
charge_behaviour    NONE | CHARGE | OTHER
op_cost             float
range               float
damage_per_shot     float
rate_of_fire        float
projectile_speed    float
flux_per_shot       float
flux_per_second     float
emp                 float
turn_rate           float
```

### 6.2 Hull table (Phase 1)

```text
id                  hull id (unique)
source              VANILLA_CORE | MOD:<modId>
hull_size           FRIGATE | DESTROYER | CRUISER | CAPITAL
role                role hint
dp                  float
op                  float
hull_hp             float
armor_rating        float
flux_capacity       float
flux_dissipation    float
shield_efficiency   float      (lower is stronger)
shield_type         NONE | OMNI | FRONT | OTHER
speed               float
maneuverability     float
mount_capacity      float      (derived, §10.0)
mount_topology_class named heuristic bucket
fighter_bays        int
system_id           string
```

### 6.3 Rules

- Table rows carry `source`. Nothing downstream is allowed to lose it.
- Parsing failures produce `NOT_DETERMINABLE` fields and a parse note — never a fabricated value (§3.2).
- A row whose required structural fields are undeterminable is excluded from the cohort pool and recorded in the report (§8.4).
- Table order never affects results (property test, §20.5).

## 7. Provider boundary

BalanceBench must be usable and testable **without** VoidSmith present. Legality/hook knowledge is consumed through a narrow provider interface.

### 7.1 Interface

```text
Provider
  hooks(entity_id)      -> list of script hook descriptors
  legality(entity_id)   -> legality facts (opaque to BalanceBench)
  completeness()        -> COMPLETE | PARTIAL | ABSENT
```

Implementations:

```text
VoidSmithProvider   preferred when VoidSmith output is available
LocalFallback       static scan of the mod tree; hooks only, partial
NullProvider        explicit, for tests and for mods with no scripts
```

### 7.2 Rules

- Provider output is **advisory input**, never authoritative for a balance verdict.
- `completeness()` flows into confidence (§14). A partial provider lowers confidence; it does not by itself force `MANUAL`.
- The provider never mutates inputs and is never required for the vanilla self-audit (§20.2), which runs provider-free.
- BalanceBench never duplicates legality logic. If VoidSmith says something is illegal, that is a separate report.

### 7.3 Why not fuse with VoidSmith

Fusing would make BalanceBench un-testable when VoidSmith changes, and would blur two different questions (legal vs balanced). The boundary keeps both honest.
