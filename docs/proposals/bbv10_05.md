## 8. Cohorts — hard structural eligibility

The cohort is an **eligibility filter**, not the evidence. Evidence comes from the selected peers (§9). Conflating the two was the v0.1 mistake.

### 8.1 Weapon cohort predicates

A vanilla weapon is eligible as a peer for candidate `C` only if:

```text
same weapon_type
same size
same damage_class
same delivery class      (beam / projectile / missile)
same ammo model          (for missiles)
same PD status
```

These are **structural / behavioural** descriptors only. No measured performance value may appear in this list.

### 8.2 Hull cohort predicates

```text
same hull_size
same role bucket
```

Role buckets are a small named set; unknown role lowers confidence and is recorded, it does not silently cross to another bucket.

### 8.3 Never cross

```text
never cross weapon type
never cross hull size
never cross damage class within a weapon family
never blend vanilla into mod corpus or vice versa
```

The first three are executable invariants (§20.5).

### 8.4 Insufficient cohorts

If the eligible vanilla pool is smaller than the policy minimum (`k_min`), the result is `MANUAL` with `manual_reason = INSUFFICIENT_PEERS`. The report still shows the pool that existed, so a human can see whether the structure or the install is at fault.

### 8.5 Excluded-but-informative

Entities excluded by the cohort rules are recorded with the **reason** (e.g. `Paladin PD — PD role mismatch`). Showing near-miss exclusions is what makes a peer set auditable (§17).

### 8.6 Mod corpus is context, not baseline

Mods may inform:
- ecosystem notes (how crowded a niche is),
- inter-mod consistency observations,
- cross-mod warnings.

Mods may **never** enter the vanilla reference distribution. There is no policy switch that permits it.

## 9. Peer selection — leakage-safe

### 9.1 The rule

> A metric being judged must never select its own comparison peers.

If range selects the peers and range is then judged against those peers, the comparison is tilted toward the candidate. This is selection leakage (a form of double-dipping). It is the single most important statistical correction in this design.

### 9.2 Two disjoint feature sets

**Selection features** (structural/behavioural, from §8.1):

```text
weapon_type, size, damage_class, role,
trigger (burst/continuous), delivery (beam/projectile/missile),
ammo_model, is_pd, turret_behaviour, charge_behaviour
```

**Scoring features** (measured values, judged later):

```text
range, DPS, damage/shot, flux efficiency,
OP efficiency, accuracy, EMP, ...
```

No feature appears in both sets for the same judgement.

### 9.3 Leave-one-feature-out mode

Some continuous values are genuinely useful for fine-grained nearest-neighbour selection. When that is necessary, selection is done with the judged metric **removed**:

```text
when scoring RANGE       -> select peers without range
when scoring OUTPUT      -> select peers without DPS / damage-per-shot
when scoring EFFICIENCY  -> select peers without OP-derived ratios
```

This produces a per-metric peer set. It is more expensive than one global peer set and analytically much cleaner. The report records **which peer set was used for which metric**.

### 9.4 Selection procedure

```text
1. hard cohort                 (§8)
2. distance in selection space (normalized structural/behavioural features)
3. take the k nearest, k in [k_min, k_max]
4. record peer ids + distances + peer quality flags
```

### 9.5 Peer quality

```text
TIGHT      peers are close in selection space; distribution is usable
LOOSE      peers are sparse or spread; widens the band, lowers confidence
DEGENERATE fewer than k_min usable peers after exclusions
```

Peer quality is reported per metric and feeds confidence (§14). It never silently changes the verdict rule.

### 9.6 Auditability

The chosen peers are listed **by id**, with distances, and the exclusions are listed with reasons. Recording peers by id is what makes a nonsense comparison visible instead of an unexplained score.
