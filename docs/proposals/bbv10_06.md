## 10. Metric Specification Registry

### 10.1 Purpose

Every scored value in BalanceBench is defined exactly once, in the registry.
No module may compute a metric with its own local interpretation of a column,
a denominator, or a direction. This removes the single nastiest long-term
failure mode of a data-analysis tool: two modules silently disagreeing about
what `dps_per_op` means.

The registry is data, not code. It is versioned with the policy (section 19)
and hashed into every report (section 17).

### 10.2 Entry schema

Each metric entry declares:

```yaml
dps_per_op:
  applies_to: weapon
  formula: sustained_dps / op_cost
  inputs: [sustained_dps, op_cost]
  units: dps_per_op
  direction: HIGHER_STRONGER
  family: EFFICIENCY
  scored: true
  transform: RAW
  denominator:
    zero: NOT_DETERMINABLE
  missing:
    sustained_dps: NOT_DETERMINABLE
    op_cost: NOT_DETERMINABLE
  applicability: "op_cost > 0 and not is_pd"
  confidence_implications: "missing input lowers confidence, never zero-fills"
```

| Field | Meaning |
|---|---|
| `applies_to` | entity kind: `weapon`, `hull`, later `fighter`, `system`, `hullmod` |
| `formula` | exact arithmetic over the declared inputs |
| `inputs` | source columns or other derived metrics |
| `units` | reported unit |
| `direction` | see 10.3 |
| `family` | aggregation family (section 12) or `DIAGNOSTIC` |
| `scored` | whether the metric participates in the family signal |
| `transform` | statistical space, see 10.4 |
| `denominator.zero` | meaning of a zero denominator |
| `missing.<input>` | meaning of a missing input |
| `applicability` | predicate; outside it the metric is `NOT_APPLICABLE` |
| `confidence_implications` | how absence affects confidence (section 14) |

### 10.3 Directionality

Exactly one of:

| Direction | Meaning | Ranking transform |
|---|---|---|
| `HIGHER_STRONGER` | larger favours the candidate | as-is |
| `LOWER_STRONGER` | smaller favours the candidate | negate before ranking |
| `NON_MONOTONIC` | an optimum lies inside the range | distance from peer median, both directions |
| `CONTEXTUAL` | no global sign exists | `DIAGNOSTIC` only, never scored |
| `DIAGNOSTIC` | reported for humans, never scored | none |

Canonical convention, stated once and enforced everywhere (section 1.6):

> positive balance excess = candidate advantage; negative = candidate disadvantage.

`NON_MONOTONIC` is a deliberately conservative starting point: distance from
the peer median is not the same as distance from a true optimum. Calibration
(section 20.6) may demote most `NON_MONOTONIC` metrics to `DIAGNOSTIC`. That is
an accepted, recorded outcome, not a bug.

### 10.4 Transforms

Statistical space is declared, never improvised:

| Transform | Use |
|---|---|
| `RAW` | default; no transform until evidence justifies one |
| `LOG` | multiplicative quantities |
| `RECIPROCAL` | reciprocal quantities (e.g. shield efficiency) |
| `RATIO_TO_PEER_MEDIAN` | scale-free comparison |
| `CUSTOM` | named formula in the registry, with a comment explaining why |

The raw value is always reported alongside the transformed value, so a human
always sees the mechanics rather than the convenience.

Transforms default to `RAW`. Clever math must not sneak in before evidence.

### 10.5 Missing and zero

- A missing input is never zero-filled.
- A zero denominator yields `NOT_DETERMINABLE` unless the entry says otherwise.
- `NOT_DETERMINABLE` removes the metric from the family signal and lowers
  confidence (section 14); it never counts as `IN_BAND`.

### 10.6 Scored versus diagnostic

- `scored: true` metrics contribute to a family signal.
- `DIAGNOSTIC` metrics are reported and may lower confidence, but can never
  change a verdict. This is an executable invariant (section 20.5).
- A metric with `direction: CONTEXTUAL` must be `scored: false`.
